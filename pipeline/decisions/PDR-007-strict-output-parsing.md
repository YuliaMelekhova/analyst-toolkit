# PDR-007 — Malformed agent output is discarded rather than repaired

---

## Context

The drafting agent is instructed to return a single JSON object containing a document body, a gap list and any assumptions. Models occasionally return that object wrapped in prose, inside code fences, truncated, or with a field missing.

A tolerant parser recovers most of these. The question is what the recovered output represents once it has been reconstructed by code that was not specified against the agent contract.

**Forces at play.**

| Force | Pulls towards |
|---|---|
| Failed executions cost the requester a wasted cycle | Salvaging what can be salvaged |
| Recovered output is not what the contract specifies | Discarding it |
| Contract violations are signals about the instruction | Making them visible rather than absorbing them |
| Salvage code is the least exercised path in the pipeline | Not having one |

---

## Decision

`DFT 04` parses strictly. Invalid JSON after fence stripping, a missing or non-array `gapList`, or a missing or empty `body` fails the execution and discards the draft. No repair, no partial acceptance, no fallback structure.

An empty `gapList` is not a violation. It is permitted and flagged to the reviewer.

---

## Options considered

### Option A — Strict parsing, discard on violation

**What it is.** Type checks on every contract field; any failure raises and the execution stops.

**Consequences.**

| Better | Worse |
|---|---|
| Contract violations are visible and countable | Some recoverable executions are lost |
| Instruction regressions surface immediately | The requester sees a failure rather than a draft |
| No unspecified document ever reaches a reviewer | Requires an error path to notify anyone, which this reference lacks |

**Why chosen.** The violation rate is diagnostic information about the instruction, and absorbing it means an instruction change that degrades output looks like nothing happening.

### Option B — Tolerant parsing with a repair pass

**What it is.** Extract JSON from surrounding prose, supply missing optional fields, accept partial structures.

**Consequences.**

| Better | Worse |
|---|---|
| Higher completion rate | Violations become invisible, so the instruction is never fixed |
| Requesters see fewer failures | Repairing a missing `gapList` manufactures a gap analysis that never happened |
| Handles transient formatting drift | The repair path is the least tested code in the pipeline |

**Why not chosen.** The specific case that condemns it is the missing gap list. Supplying an empty array there produces a draft that tells the reviewer the agent found nothing missing, when in fact the agent said nothing at all. That is a fabricated assurance generated by the pipeline itself.

### Option C — Strict parsing with capped retry

**What it is.** Option A, plus a bounded number of retries before failing.

**Consequences.**

| Better | Worse |
|---|---|
| Absorbs transient formatting failures without hiding systematic ones | Additional cost per failed execution |
| Retry count is itself a useful signal | Needs a cap, a backoff and a budget, none of which are defined here |

**Why not chosen for this reference, and recommended for a deployment.** Omitted only because an uncapped retry against a paid API is a cost incident waiting to happen, and specifying the cap properly is deployment-dependent. This is the option a real installation should take.

---

## Consequences

**Accepted costs.**

- Transient API or formatting errors discard a request entirely and the requester must resubmit.
- No output at all is produced in cases where a partial document would have been useful.
- Without an error workflow, a failed execution is currently silent to everyone but the maintainer.

**What becomes harder.**

- Operating the pipeline without monitoring, since failures are the mechanism and nothing surfaces them.
- Tolerating a model or provider change that alters output formatting, which will show as a failure spike rather than degraded drafts.

**What this closes off.**

- Any partial-credit handling of agent output. The contract is satisfied or it is not.

---

## What would change this decision

| Trigger to revisit | How we would notice | Who watches for it |
|---|---|---|
| Parse failure rate becomes an operational problem | Contract violation rate by cause (`metrics.md`) | Pipeline maintainer |
| Failures cluster on one request type | Violation rate segmented by type | Pipeline maintainer |
| A model change alters output formatting systematically | Failure spike coinciding with a version change | Pipeline maintainer |

In all three cases the instruction is the thing to fix, not the parser.

---

## Assumptions this rests on

| Assumption | If false, the decision | Confidence |
|---|---|---|
| Violation rate is low enough that discarding is affordable | needs revisiting; Option C becomes necessary | medium |
| Failures will be noticed by someone | is wrong today; there is no error workflow | low |
| The instruction can reliably produce conforming output | still holds; a high rate would indicate an instruction defect | high |

---

## Not decided here

- Retry policy, cap and backoff. Recommended and unspecified.
- What the requester is told when an execution fails. Currently nothing.
- Whether partial drafts have any value worth capturing. Assumed not.
